Cadence options and meeting-date backfill

Date 2026-06-20  ·  Topic cadence-and-meeting-date  ·  Mode repo-grounded  ·  Focus two post-testing feedback items on meeting-assistant.tsx

Two pieces of feedback — "let me pick a daily / custom-weekday cadence" and "stop assuming a note pasted today means the meeting happened today" — turn out to touch the same machinery and form one small, coherent system. The load-bearing, non-obvious finding: capturing a meeting date does nothing on its own. The follow-through engine ages every commitment off last_touched (ingestion time), never the provenance date — so a date feature that only relabels provenance is cosmetic. The keystone is re-anchoring that clock.

Grounding Context

Codebase machinery (verified by a code scout against meeting-assistant.tsx) plus external prior art.

Cadence is load-bearing, not a label

type Cadence is a bare string union (:332) of Weekly/Biweekly/Monthly/Ad hoc — no Daily, no Custom. It is used as a key into CADENCE_DAYS (:110) at the one load-bearing site (:620): interval_days = CADENCE_DAYS[cadence] ?? DEFAULT_STALE_DAYS. That interval_days is the staleness threshold for the whole follow-through engine. An unknown key falls back to 14 days silently. Cadence is also string-interpolated into the LLM extraction prompt (:1143) and rendered directly as a React child (:3613, :3987).

The "assumes today" problem lives in three places

Note timestamp = nowISO() (:1027); item provenance source.date = nowISO() (:1933/:1937); and the extraction anchor ctx.today (:1950) that the model uses to resolve "by Friday" into a calendar date (:1159). last_meeting_date (:393) is dead/vestigial — set null at creation and never written again.

The critical decoupling

The staleness clock reads last_touched (:464), not source.date (which is provenance-display only). last_touched is set to ingestion now at every write site (:1390, :1437/:1444, :2090, :2167, :2191). isUntouchedStale (:1524–1527) is the only consumer of interval_days. So backfilling a date changes labels only unless last_touched is also seeded from it.

Migration is a silent-failure seam

SCHEMA_VERSION = 2 (:89); normalizeImport (:1789) spreads meetings verbatim and validateImportStructure (:1738) checks only id/name, so cadence shape is never normalized or validated. fmtDate (:2888) renders month+day with no year. There is no guard against a future-dated value.

External prior art

The minimal recurrence model is the RRULE subset {freq, interval, byweekday} — ~15 lines of native JS, no library (RFC 5545; Google Calendar's custom dialog exposes exactly these three fields). AI extraction of explicit dates runs ~84–90% accurate when anchored to a known "today." Event-time vs ingestion-time is a settled question: anchor aging to the event (meeting) date, fall back to ingestion only when no date is known (Confluent/Kafka watermarks; Obsidian Tasks anchors overdue to due-date; Apple EventKit conflating the two is a documented anti-pattern). The "Intent Preview" pattern (propose → approve/edit/skip with the source snippet) is already the app's verification-screen idiom.

Topic Axes

The surface these ideas were generated and spread across.

  • Cadence representation — how recurrence is typed and stored; Daily vs structured Custom; how interval_days is derived.
  • Cadence editor UX — capturing interval + weekdays in a no-<form>, select-based picker.
  • Date capture — manual override vs AI inference from note text, and the confirm flow.
  • Staleness-engine coupling — event-time vs ingestion-time; whether a backfilled date seeds last_touched, overdue, and the cockpit.
  • Migration & data integrity — schema bump, legacy-cadence normalization on import, year-ambiguous dates, future-date guards.

How these fit together

The run's headline: convergence, not a feature menu. There is a build order and one sequencing trap.

One compound, one trap

The compound (5 of 5 frames found it): date capture (idea 2) and event-time staleness (idea 1) must ship together. Capture a date without re-anchoring last_touched and the feature looks done but does nothing; re-anchor without capturing a date and there is nothing to anchor to.

The trap (surfaced in verification): saveRawNote stamps the date at save-time, but an AI-inferred date isn't confirmed until the verification screen, after the save that the "save-before-analyze" rule (R3) deliberately does first. So a manual date set at capture-time is clean, while an AI-inferred date needs a post-accept patch that rewrites source.date + last_touched on the accepted items. This is the load-bearing implementation detail and an open question for brainstorm.

1.

Event-time staleness — anchor the aging clock to the meeting date

Keystone
axis Staleness coupling conf 90% · High cx Medium

Description. Today every commitment's staleness clock (last_touched) starts the moment notes are pasted, not when the meeting happened. Seed last_touched — and the provenance source.date — from the confirmed meeting date, falling back to ingestion time only when no date is known. No new field is needed: source.date already plays the event-date role and created_at/note.timestamp already preserve the ingestion instant for audit.

Basis

directlast_touched is set to nowISO() at every write site (:1390, :1437/:1444, :2090, :2167, :2191) and isUntouchedStale (:1524–1527) reads only last_touched, never source.date. externalevent-time vs ingestion-time is settled in stream processing (Confluent/Kafka watermarks); Obsidian Tasks anchors overdue to due-date not created-date; EventKit conflating the two is a documented anti-pattern.

Rationale

The one change that makes backfill behaviorally real. Without it, every other date idea is cosmetic. Five of five ideation frames converged here independently.

Downsides

Inherits the write-ordering trap (see "How these fit together"): the AI path needs a post-accept patch of source.date + last_touched. Backfilled items may surface as stale the instant they're accepted — usually correct, but a UX call. Pair with the future-date guard (idea 6).

2.

One meeting-date, two inputs — manual at capture, AI-inferred at verify

axis Date capture conf 80% · High cx Medium

Description. Model the meeting date as a single confirmed value with two ways to set it, differing only by a provenance flag (manual | inferred | default). The same call's relative-date anchor (ctx.today) should point at the confirmed date so "by Friday" resolves to the right week.

Manual — at capture

Optional date field on the capture screen, defaults to today. Zero extra taps for real-time notes; one tap to backfill. Set before save — clean ordering, no patch needed.

AI-inferred — at verify

Extraction returns one extra field {meeting_date, confidence, source_snippet} (no second call), confirmed on the existing verification screen. Low-confidence or absent → silent fall back to today.

Basis

directthe extraction prompt already receives ctx.today (:1159) and returns per-item due_date, so one extra scalar is ~15 tokens of the 1000-token budget; source.date = nowISO() (:1933/:1937) is the single origin to replace; the verification/confirm screen already exists. externalGPT-class models hit ~84–90% on explicit dates when anchored to a "today"; the "Intent Preview" pattern is exactly the app's verification idiom.

Rationale

Covers Bryan's "AND/OR" with one field and one downstream code path — the manual picker doubles as the correction for a wrong inference. Reusing the verification screen adds no surface and keeps the trust model: a date the engine ages from is human-confirmed, never silently inferred.

Downsides

The AI path lands after save, so it needs idea 1's post-accept patch (the manual-at-capture path avoids this). AI inference can't be tested locally. Optional lighter variant: a ~20-line native-Date regex for explicit formats (2026-06-18, 6/18, Jun 18) handles the common case with zero tokens and is unit-testable in the dev harness — but it adds code surface and the AI works in production, so it is an option, not a requirement.

3.

Add "Daily" now; structure cadence as {freq, interval, byweekday} for Custom

axis Cadence representation conf ~75% · High (Daily) / Med (Custom) cx Low → Medium

Description. Two points on one spectrum. Floor: add "Daily" with three additive edits (Cadence union :332, CADENCE_DAYS :110, CADENCES :3499) — no schema bump, since interval_days is derived at ledger-build (:620), not stored. Complete: to satisfy the Outlook-style Custom ask (frequency + specific weekdays), widen Cadence from a bare string into a small structured value {freq:"DAILY"|"WEEKLY", interval, byweekday[]} and derive interval_days from it. Presets become sugar over the same shape.

Basis

directtype Cadence is a bare string union (:332) used as a CADENCE_DAYS key (:620, silent 14-day fallback), string-interpolated into the LLM prompt (:1143) and rendered as a React child (:3613, :3987) — so a structured value needs a cadenceLabel() formatter at those sites or it prints [object Object]. externalthe RRULE subset FREQ/INTERVAL/BYDAY is the minimal model (RFC 5545; Google Calendar), ~15 lines of native JS.

Rationale

"Daily" alone is a genuine half-day v1 that unblocks the common standup case immediately. But Custom-by-weekday is explicitly what was asked, and a string enum can't express it without becoming structured somewhere. Doing the object once makes Daily, every-weekday, and Mon/Wed/Fri all fall out of one representation — and later powers a next-meeting scheduler and the dead last_meeting_date field.

Downsides

The string→object change is the heaviest lift in this set: it ripples to every interpolation/render site and forces the schema bump + import normalization (idea 6). Verification flagged the object as premature complexity (no scheduler or ICS export exists yet) — a fair YAGNI caution: if Custom is deferred, ship "Daily" alone and skip the upheaval. A compact string encoding ("W:1,3,5") is a lighter middle path but harder to validate and migrate than a typed object.

4.

Make staleness correct for short and multi-day cadences

axis Cadence representation conf 75% · Med-High cx Low-Medium

Description. Two coupled tunings so richer cadence doesn't break the cockpit. (a) Density-derived interval: for a Custom weekday set, derive interval_days from the largest gap between selected days (Mon/Wed/Fri → 3, not 7), because the engine treats interval_days as a literal "go stale after N silent days" deadline. (b) A per-cadence quiescence floor so a Daily meeting (interval 1) doesn't nag the morning after every silent day and train the user to ignore the cockpit.

Basis

directisUntouchedStale (:1526) compares now - last_touched > interval_days — a hard deadline, so an inflated value silently suppresses resurfacing, the opposite of the engine's job; TUNING (:93) already establishes the named-constant pattern a floor would use. reasoneda conservative "7 for any weekly-with-weekdays" is wrong precisely because timely resurfacing is the whole point; the gap-based number matches how often the meeting actually happens.

Rationale

The non-obvious catch the naive build gets backwards. Adding Daily/Custom without it makes multi-day meetings age slower than today's presets and daily meetings flood — either way the follow-through engine gets less trustworthy as cadence gets richer.

Downsides

Both numbers are judgment calls that need calibration at first paste-in (joining the existing deferred-tuning list). A floor set too high mutes legitimately-stale daily items.

5.

Custom recurrence picker — weekday chips + interval stepper + live next-date preview

axis Cadence editor UX conf 80% · High cx Medium

Description. When "Custom" is selected in the setup modal, reveal an inline builder: a 7-button weekday toggle row (aria-pressed, no checkboxes), an interval stepper (two buttons, no <input type=number>), and a live computed line — "Every 14 days · next Jun 27" — that shows the derived interval and next occurrence as the rule is built. All onClick + React state, satisfying the no-<form> constraint.

Basis

directthe only cadence editor today is a single <select> (:3520) fed by CADENCES (:3499) with an e.target.value as Cadence cast — phone-hostile and unable to hold interval+weekday state. externalGoogle Calendar's custom-recurrence dialog is exactly this shape; aria-pressed toggle buttons are the standard accessible substitute when <form> controls are unavailable.

Rationale

The literal surface Bryan asked for ("pick cadence + days of the week"). The live preview closes the loop between what is being picked and when it will resurface, making the otherwise invisible link between cadence and the staleness engine legible at setup time.

Downsides

Real UI work, and it depends on idea 3's structured representation to have something to pick into. Needs a sensible mobile layout for the weekday row.

6.

Migration and integrity bundle

axis Migration & integrity conf 85% · High cx Medium

Description. The safety net both features require, as one unit: bump SCHEMA_VERSION to 3; add a single normalizeCadence() chokepoint called on both in-place load and import so legacy string cadences map to the new shape (and unknown values default explicitly, not silently to 14 days); validate cadence shape in validateImportStructure; make fmtDate emit the year when a date isn't in the current calendar year; and guard a future-dated value — a fat-fingered forward date becomes a visible "held until <date>" state rather than silently disabling aging.

Basis

directSCHEMA_VERSION = 2 (:89); normalizeImport (:1789) spreads verbatim and validateImportStructure (:1738) checks only id/name, so a structured cadence with no normalization degrades every imported meeting to the 14-day fallback (:620); fmtDate (:2888) has no year; a future last_touched makes now - last_touched negative so isUntouchedStale never fires. externalthe watermark idea — hold late/future events rather than mis-age them.

Rationale

Import is the only bridge between artifact versions (a new artifact is empty storage), and this is a trust-first app — a silent cadence corruption or an invisible item on a typo'd date is exactly the quiet failure that erodes the follow-through engine. One normalize chokepoint beats scattered checks.

Downsides

Couples shipping to a schema migration and its import path; the year-aware fmtDate is trivial but the normalize/validate work is real. Mostly invisible to the user (correctly).

7.

Infer cadence from the meeting-date history

axis Cadence editor UX conf 55% · Medium cx Medium-High

Description. Once meetings actually carry dates (ideas 1–2), observe a meeting's real rhythm from the gaps between dated notes and propose a cadence ("Looks like this meets about every 2 weeks — set to Biweekly?") through the same confirm idiom, instead of asking up front. Because interval_days is computed per-write at ledger-build, cadence can even change over a meeting's life without rewriting history — old items keep the interval they were stamped with.

Basis

directinterval_days is derived at ledger-build from the meeting's current cadence (:619–620), so there's no stored history to migrate when cadence changes; last_meeting_date is dead/vestigial (:393, never written after :1017) and is exactly the field an observed-date stream would revive. externalthe same event-time/watermark logic (rhythm inferred from observed events).

Rationale

Turns cadence from a thing the user must guess into a thing the app notices, and revives the dead last_meeting_date/scheduler hole as a side effect. The compounding payoff of having real dates.

Downsides

Strictly depends on the date features landing first — with last_meeting_date dead today there is nothing to infer from, which is why it ranks last. Needs 2–3 dated points before it's meaningful, and a wrong suggestion must be easy to decline.
