The AI-Proposed Tag Confirmation Model

When the extractor proposes a project tag for an item, what should happen to it? Today one amber pill produces two opposite outcomes from hidden state. This is the spread of directions for fixing that, with one recommended spine.

The problem

The extractor can attach one proposed project tag to each item it pulls from a note, stored as project_proposed_name. In the Verification surface the proposal shows as an amber dashed pill: Tag: Atlas migration?. On Accept, the same pill resolves two completely different ways depending on state the user cannot see.

This is not only a usability problem. Two of the project's own written laws are broken:

  • R20 is violated. The surface spec states "Accept never auto-confirms inference" (surface-specs.md:200). The existing-match auto-apply (onAccept, tsx:3254-3264) does exactly that.
  • The Inferred Ink Rule is violated. DESIGN.md says an inferred-but-unconfirmed value renders in secondary-text gray with a dotted underline and a small "inferred" tag, and "Not a pill" (DESIGN.md:250, :346). The proposal uses an amber fill pill, which also spends the scarce amber "do-next" signal on something that is not a next action (the One Voice Rule).

One more fact, verified against the code and worth keeping in view: a non-applied proposal is not merely orphaned, it is destroyed. proposalToItem (tsx:1385-1399) writes only project_id; the saved Item has no project_proposed_name field. So a good new-project suggestion the user does not act on vanishes at commit with no record.

Grounding Context

Codebase Context

  • Both existing-match and new-name proposals land in project_proposed_name at extraction (tsx:1249-1257); the split fires only in onAccept (tsx:3254-3264).
  • The proposed-tag pill renders identically for both cases (tsx:3113-3116). Confirming is a 2-click opt-in: tap the pill, then tap "Confirm tag" in a row that is hidden until then (tsx:3126-3131). No bulk confirm.
  • The due-date field already does inference correctly: secondary-text, dotted underline, "inferred" label, with a one-tap flip to a confirmed Indigo check (tsx:3162-3169). Owner has the same one-tap flip (tsx:3090, :3096). The tag is the one inferred field that does not follow the pattern.
  • The DestinationPicker has a structural no-inference guarantee: nothing is highlighted on open, a stray Enter does nothing (tsx:2679, :2752). It groups Recent / Meetings / Projects and has no "Recommended" concept.
  • The extraction prompt instructs the model to use exactly one existing project name or null (tsx:1140-1141). A non-matching name is therefore off-spec output, not a designed capability.
  • Constraints in force: single .tsx file, React plus lucide-react only, no <form>, window.storage (last-write-wins), schema bumps discouraged and gated on sign-off, AI calls are keyless with max_tokens 1000, no green in the palette, amber is the single scarce signal.

External Context

  • Linear Triage Intelligence is the closest precedent: it proposes team/project/label per issue, defaults to suggest-only with human approval, and makes auto-apply opt-in and configurable per-property and per-value, marking applied suggestions distinctly from human-set values.
  • No leading product auto-applies an item-level categorical value without an explicit action unless a rule was pre-configured. Ghost-text systems (Smart Compose, Copilot) make ignoring the natural non-apply; Grammarly and Notion require an explicit accept and keep a persistent provenance marker. Gmail's opt-out category tabs are the anti-model (persistent user backlash).
  • "Undo beats confirm" holds only when the action is trivially and visibly reversible. It breaks when the user may never notice the action happened, which is the case for a silent tag on a buried to-do.
  • Autocomplete default-highlight hazard (Baymard): surfacing "Suggested: X" at the top of a list is safe; pre-highlighting it so Enter selects it inflates accidental commits.

The shape of the decision

The ideas below converge on a coherent model rather than a grab-bag. The one question that has to be answered first is the policy fork: should an unconfirmed AI tag ever be applied without an explicit touch?

Recommended · ratify by default

Nothing applies without a touch

  • Honest by construction: the "?" always means "confirm me."
  • Restores R20; aligns the tag with owner and due-date.
  • Friction is bounded by one-tap confirm and a bulk confirm-all.

Counter · keep auto-apply

Auto-apply existing matches, add a loud undo

  • Zero clicks for the correct, common case.
  • Self-refutes here: Accept navigates away from Verification, so a 5s undo banner is unreachable by the time it renders.
  • Leaves R20 violated.

Ranked Ideas

Jump to

  1. Ratify by default (resolve at extraction)
  2. Inferred Ink for proposed tags
  3. One-tap confirm
  4. Bulk "Confirm all suggested tags" + undo
  5. Handle new-name proposals honestly
  6. "Recommended" at top of the picker
  7. Inferred confirmation as a reusable primitive
1

Ratify by default: nothing auto-applies on Accept

Top pick Axis AConfidence 90%Complexity Medium

Remove the existing-match auto-apply so a proposed tag becomes real only when the user confirms or retags it. The clean implementation moves the existing-match decision from Accept back to extraction (buildProposalsFromParsed, where projByName is already computed), so onAccept stops touching tags entirely and the R20 violation becomes structurally impossible rather than patched. This is the direct answer to the originating question: no, an unconfirmed tag never applies without a touch.

Axis
A · Default-on-accept policy
Basis
direct: onAccept auto-applies existing matches at tsx:3254-3264, contradicting surface-specs.md:200 "Accept never auto-confirms inference (R20)." external: Linear Triage defaults to suggest-only with human approval. reasoned: one affordance producing two outcomes from hidden state is a defect; collapsing to a single outcome removes it.
Rationale
It is the smallest change that makes the spec true again, and it removes the hidden split at the root. Resolving at extraction is strictly better than deleting the branch in place, because it leaves no tag logic in the commit path to drift.
Downsides
The user who currently coasts on auto-apply for obvious matches now has to touch them. That cost is what ideas 3 and 4 exist to neutralize; without at least one-tap confirm, this would feel like added friction.
2

Inferred Ink for proposed tags: retire the amber pill, drop the "?"

Axis CConfidence 92%Complexity Low

Render an unconfirmed proposed tag the way the design system already prescribes for inference: the project name in secondary-text gray with a dotted underline and a small "inferred" label, no fill, no question mark. Confirming flips it to the solid Indigo-check project pill. The pattern already exists two rows down on the due-date field, so this is reuse, not invention. The word "inferred" carries the not-yet-confirmed meaning, so the lying "?" disappears.

Axis
C · Visual signaling & affordance
Basis
direct: DESIGN.md:250 Inferred Ink Rule (secondary gray + dotted underline + "inferred", "Not a pill" at :346); the amber pill at tsx:3113-3116 breaks it and the One Voice Rule; the correct pattern is already implemented for due-date at tsx:3162-3169.
Rationale
This fixes two design-system violations with a pattern that already ships in the same component, so consistency is provable by eye. It also frees the scarce amber signal to mean only "do next."
Downsides
Inferred Ink is quieter than amber, so a proposed tag draws less attention. That is the intended trade (a proposal should be calm, not alarming), but if the goal were to push the user to tag, a louder treatment would do more.
3

One-tap confirm

Axis DConfidence 85%Complexity Low

Collapse the two-click confirm (tap pill, then tap "Confirm tag" in a revealed row) into a single tap that flips the inferred tag to confirmed in place, matching how owner and due-date already work. After idea 2 lands, the dotted underline is the affordance that signals "tap me," so the gesture is consistent across every inferred field.

Axis
D · Confirmation mechanics & cost
Basis
direct: owner and due-date already use a single-tap inferred-to-confirmed flip (tsx:3090, :3096); only the tag uses the hidden two-click row (tsx:3126-3131). reasoned: the only honest defense of auto-apply is "it saves clicks"; making confirm a single tap removes that defense.
Rationale
It makes ratify-by-default cheap, and it unifies the tag interaction with the rest of the surface so there is one mental model for confirming any inferred value. A typical batch of four proposals drops from eight clicks to four (and to one with idea 4).
Downsides
A single tap on a tag must be clearly distinct from navigating to the project, or a confirm could read as a jump. Worth a quick live check.
4

Bulk "Confirm all suggested tags" with undo

Axis DConfidence 72%Complexity Medium

Add a single header or bottom-bar action that confirms every live existing-match proposal in one deliberate, visible click, with a transient "N applied · Undo" affordance reusing the existing dismiss-undo timer. This is the friction antidote that makes ratify-by-default viable when a note produces several tagged items, and because the action stays inside Verification (unlike Accept), its undo is actually reachable.

Axis
D · Confirmation mechanics & cost
Basis
external: Linear offers per-property batch approve; automation-complacency research prescribes targeted (not zero) friction. direct: TUNING.DISMISS_UNDO_MS already implements the undo-timer pattern (tsx:104); there is no bulk confirm today.
Rationale
It preserves the speed of the common case (one click for all obvious matches) while keeping the act explicit and reversible, which is the combination the evidence supports.
Downsides
Its value depends on idea 1 winning the fork; if auto-apply stays, this is moot. A bulk confirm can also relocate complacency to a single button, so the undo and the count must be genuinely visible.
5

Handle new-name proposals honestly

Axis BConfidence 84%Complexity Low

A proposed name that does not match an existing project is off-spec model output (the prompt only offers existing names) and is destroyed silently today. Two honest options: (a) strip the non-matching name at parse time so it never appears as a proposal, or (b) render it as visibly distinct (a "new project" glyph or label) so the user can see it would create rather than link. A near-free compounding effect: once a user confirms a new project, its name enters the next extraction's name list, so the new-vs-existing divergence shrinks over time on its own.

Axis
B · Existing vs new divergence
Basis
direct: the prompt instructs "exactly one existing project name or null" (tsx:1140-1141); projByName already distinguishes match from non-match at build time (tsx:1249-1257). reasoned: two different outcomes deserve two legible affordances, or one of them should not be offered at all.
Rationale
It closes the most insidious half of the bug: the good suggestion that disappears with no trace. Option (a) is the simpler, lower-risk path; option (b) keeps project creation possible from the proposal but makes it deliberate.
Downsides
Option (a) removes the ability for the model to ever suggest a brand-new project from a note, which is a small capability loss. Option (b) keeps it but adds a second visual state to design. This is the one place to decide how much you value model-suggested project creation.
6

"Recommended" at the top of the picker, without pre-selection

Axis CConfidence 70%Complexity Low

The original request, made safe against the picker's no-inference guarantee. When a proposal opens the DestinationPicker, surface the recommended project in a "Recommended" group pinned above Recent (or pre-seed the search query so the list filters to it), but keep nothing highlighted, so a stray Enter still does nothing. Surfacing the recommendation collapses the scroll; pre-selecting it would reintroduce the accidental-commit hazard the picker was built to avoid.

Axis
C · Visual signaling & affordance
Basis
direct: the picker keeps active = -1 on open and a stray Enter is a no-op (tsx:2679, :2752); pinning a top group preserves that. external: Baymard: surface "Suggested: X" at the top, do not pre-fill a field that submits on Enter.
Rationale
It delivers the literal ask (the recommendation is one click away, no scrolling) and threads the exact tension the picker's design was built around. Its value rises once ratify-by-default makes the picker a more common confirm path.
Downsides
On its own this is the smallest idea here, more polish than decision. Pre-seeding the query is the lighter build but can briefly surprise a user who opened the picker meaning to search for something else.
7

Inferred confirmation as a reusable primitive

Axis ALeverageConfidence 75%Complexity Low

Rather than fixing the tag in isolation, name the pattern: Inferred Ink plus one-tap confirm plus "Accept never applies what was not confirmed" becomes the convention that governs every inferred field. Due-date and owner already follow it; the tag is the laggard; any future inferred field (priority, for example) inherits it for free. This turns a one-off fix into a system rule.

Axis
A · Default-on-accept policy (leverage)
Basis
direct: the inferred: { due, owner } object already models this (tsx:1074) and the visual treatment ships for due-date and owner. reasoned: a single convention prevents each new inferred field from re-litigating the confirm question, and keeps the design system honest by leaving no exceptions.
Rationale
Highest-leverage framing in the set: it is mostly consistency work, and it makes the tag fix the template the rest of the app follows rather than a special case.
Downsides
It is a framing more than a feature, so its payoff is realized only when future inferred fields actually arrive. Worth adopting as a stated convention even if the immediate code change is just the tag.

Axis coverage

Survivors spread across axes A, B, C, and D. Axis E (reversibility and recovery) has no standalone survivor by deliberate choice: the loud-undo counter-proposal self-refutes because Accept navigates away from Verification, and post-accept recovery of a dropped suggestion needs an additive Item.project_proposed_name field (proposals are destroyed at commit today), which is a data-model change gated on your sign-off. Reversibility is partially served by idea 4's undo on bulk confirm. If recovering dropped suggestions matters to you, that schema question is the thing to raise next.
